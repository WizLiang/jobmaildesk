# 维护、更新与发布

当前维护范围是 Windows x64。macOS 构建仅手动选跑，不是当前 Windows 交付的必选门禁；Android 暂不在本轮范围内。产品与隐私约束见 [PROJECT_RULES.md](../PROJECT_RULES.md)，发布逐项核对 [RELEASE_CHECKLIST.md](RELEASE_CHECKLIST.md)。

## 先区分三件事

| 操作 | 完成标志 | 用户得到什么 |
| --- | --- | --- |
| 推送分支 | 远端分支包含已验证的提交 | 源码备份与 CI 结果；默认首页和安装包不一定改变 |
| 合并主线 | PR 检查通过并合并到 `main` | 默认源码、README 和维护文档更新 |
| 发布程序 | 唯一版本标签构建成功，Release 资产复验通过 | 可下载的新包，符合通道的用户可在程序内更新 |

`main` 是唯一正式主线，不直接在其上开发。使用单一目标的短期分支，如 `agent/<主题>`、`fix/<主题>`、`feature/<主题>` 或 `docs/<主题>`。只有应用、依赖、兼容性或安装内容发生可交付变化时才发包；文档修改通常随下次产品版本一起发布。

正式版本必须来自经过 PR 合并的 `main`。当前已获授权的 Windows 试用版可以从通过验收的功能分支发布唯一 `rcN` 标签，始终标为 prerelease；PR 权限不足不阻断这种试用分发，但必须说明源码尚未合并，后续仍需补齐 PR。不得把“已发布 RC”说成“已合并主线”或“正式版验收完成”。

## 日常修改

1. 检查工作树和远端状态，阅读项目规则、相关项目记忆与测试。通常从最新 `main` 开始；主线尚未接收已发布 RC 时，从对应 RC 提交继续，并在 PR 中说明基线。
2. 先复现再修复。解析修改补匿名 golden vector；申请链、去重、状态或同步修改补服务回归。不得把真实邮箱、授权码、邮件正文、Message-ID、私人链接或个人路径写入测试与日志。
3. 先运行受影响的测试。用户可见变化写入 `CHANGELOG.md`，同步对应使用文档；UI 修改检查正常尺寸、字体缩放、空状态和错误反馈。
4. 准备提交时运行完整测试、秘密扫描、版本一致性和差异检查。只暂存本阶段文件，形成可回滚提交，推送并核对提交 SHA 与 Windows Actions 结果。
5. PR 说明问题、结果、验证、数据兼容性和回滚方式；检查通过再合并。只删除已经合并且不再承载后续工作的分支，保留历史标签与 Release。

在仓库根目录使用 Python 3.12 与锁定依赖：

```powershell
uv sync --frozen --group dev
python scripts/version.py check
uv run --frozen pytest
powershell -NoProfile -ExecutionPolicy Bypass -File .\scripts\secret-scan.ps1
git diff --check
```

如系统没有 Python 3.12，可将版本命令中的 `python` 换成 `uv run --frozen python`。这些命令仅验证源码；完整发布还须验证包和使用流程。

纯日常求职进度更新遵循项目规则中的稳定 ID 写回流程，不进入版本、Git 或打包流程。

## 版本号

版本使用 `MAJOR.MINOR.PATCH`，试用候选在后面加 `rcN`，例如 `0.7.0rc2 → 0.7.0rc3`。同一批试用反馈递增 RC；修复已发布正式版递增 PATCH，兼容新功能递增 MINOR，破坏兼容的变化必须显著说明迁移方式。试用阶段不要只去掉 RC 后缀就宣称稳定。

统一通过脚本同步版本字段，避免手改遗漏：

```powershell
python scripts/version.py set 0.7.0rc3
python scripts/version.py check
```

后续候选把参数换成选定的 `0.7.0rcN`。脚本同步 `pyproject.toml`、`src/job_mail_desk/__init__.py` 与 `uv.lock` 的项目版本；Release 标签采用相同版本加 `v`，如 `v0.7.0rc3`。Changelog、当版 Release Notes、验收记录和下载说明仍需人工审阅；历史发布文档不批量替换版本号。

CI 与本地构建自动执行版本检查；打包还核对源码版本与两个 EXE 的产品版本，拒绝把旧程序重新标成新版本。

已发布标签、ZIP 和校验文件不可覆盖、删除或重新指向。发现问题，保留原版本记录，发布更高 RC 或 PATCH。

## 一轮发布只交付一次

开发期间保持 Release Freeze：集中修复、验收、冻结范围，再一次创建标签。允许阶段提交、PR 和 Actions 构建产物；不要每改一个按钮就发新版本。

RC 发布前必须完成自动化、秘密扫描、版本校验、Windows 构建、包内容检查与隔离空数据自检。原生交互、真实邮箱只读回归或长期试运行未完成的项目必须在验收记录和发布说明中明确列出；不能以自动测试代替，也不能带着已知隐私泄露、数据损坏或安装阻断发布。

正式版还必须关闭人工验收项：首次配置、缓存启动、扫描与退出、重复运行、旧数据兼容，以及启用时的台账/Obsidian 往返同步；真实邮箱检查保持只读并验证邮件状态不变，记录不得包含私人邮件数据。至少完成三天真实环境试运行，并满足 Windows 签名要求；在此之前只分发 prerelease。当前工作流始终创建 prerelease，不能仅凭无 RC 后缀标签提升为正式版。

发布顺序：

1. 冻结本轮范围，运行版本同步脚本。整理 `CHANGELOG.md` 当版条目，创建版本完全匹配的 `docs/RELEASE_NOTES_v<版本>.md` 与 `docs/ACCEPTANCE_v<版本>.md`，写清升级方式、已知限制与实际验证结果。
2. 完成 [发布清单](RELEASE_CHECKLIST.md) 的本地门禁，将远端构建待验项目明确记录。提交并推送，核对 Windows CI；正式版本先完成 PR 合并，RC 可使用上述已授权分支例外。
3. 确认所选提交和版本无误后，在该提交创建唯一附注标签并推送，例如 `git tag -a v0.7.0rc3 -m "JobMailDesk 0.7.0rc3"`、`git push origin v0.7.0rc3`。这些命令属于实际发布操作，不用于检查版本。
4. 标签触发 `.github/workflows/build-core.yml`。Windows 测试、秘密扫描、构建与空数据自检通过后，工作流发布 ZIP 和对应 `.sha256`，共两个资产。macOS 手动验证不自动增加本次 Release 资产。
5. 从已发布的 Release 重新下载 ZIP 与校验文件，核对版本、文件名、SHA-256、解包内容和包内自检。检查发布说明、README 下载入口与程序内的预览/正式通道行为。远端未完成时不得报告“发布成功”。

## 更新和数据兼容性

- 程序与用户选择的数据目录分离；更新只替换程序，不迁移或删除用户数据、配置、系统凭据和外部 Markdown。
- 任务与申请事实、稳定 ID、忽略/删除/结束状态优先级必须保留；新字段有默认值，迁移幂等，SQLite 与首屏缓存可重建。
- 新更新器仅访问 `WizLiang/jobmaildesk` 的公开 Release。每日检查默认关闭；自动检查只提示，下载和重启替换分别需要用户主动操作。客户端不需要 GitHub 凭据，也不上传邮箱或求职数据。
- 更新链路回归覆盖通道和版本排序、断网、损坏校验文件、缓存被改、恶意 ZIP 路径、目录权限、数据目录重叠、旧进程未退出、替换失败与恢复。更新和数据迁移/清除互斥。
- SHA-256 用于核对下载内容，不是独立代码签名。不得把校验通过描述为签名认证。
- Windows 替换前保留同级旧程序备份；失败尝试恢复。更新后程序启动失败时，先退出全部实例，再从备份恢复程序，保留数据目录；不得通过删除用户数据解决升级故障。操作说明见 [UPDATES.md](UPDATES.md)。

## 后续维护

- 用户反馈优先收集版本号、复现步骤和脱敏截图；不索要授权码，不要求把真实邮箱或完整数据目录上传 GitHub。
- 每月检查直接依赖、锁文件、GitHub Actions 与 Python 3.12 兼容性，按批次升级并回归，不无差别重解依赖。
- 已合并未发布的问题，用新的修复或反向提交处理，不强推 `main`；已发布问题在原公告说明并发布更高版本，保留原标签和资产。
- 隐私、凭据或数据损坏问题可优先发布必要修复，但仍需与风险对应的完整验收。
- 发布后清理本轮临时测试/构建文件，只处理已确认属于工作目录的产物；保留验收记录与需要的回滚包，不触碰真实数据或仍在使用的程序。
